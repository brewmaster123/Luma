# Luma 0.9.5 (21)

Продолжение 0.9.4 (20). Умный будильник, непрямой метод и проба снова используют AlarmKit по прямому запросу пользователя. Код, ресурсы, Xcode-проект и CI находятся в этой папке. Исторические версии не изменены.

Это версия для проверки гипотезы: передавать AlarmKit собственный четырёхсекундный WAV и позволить файлу закончиться естественно. **Самостоятельное прекращение звука на заблокированном iPhone ещё не подтверждено.** Длительность файла не доказывает, что система не проиграет его снова.

## Что реализовано

- Общий AlarmKitScheduler для обоих режимов. Каждый сигнал — отдельный UUID и fixed date. Нет snooze, повторного countdown, стандартного звука при ошибке или постановки локального уведомления вместо будильника.
- Отдельный ресурс Luma/Resources/luma-alarm-4.wav: PCM16 mono, 22 050 Гц, 88 200 отсчётов, 4,000 секунды. Мелодия заканчивается плавно; WAV не содержит smpl/plst меток зацикливания.
- Голоса и мелодии преобразуются в отдельный Library/Sounds/luma-ak4-<SHA256>.wav. Длинный материал ограничивается четырьмя секундами, короткий дополняется тишиной. Оригиналы сохраняются. Новый кэш v4 не использует старые CAF.
- После наблюдения состояния alerting работающий процесс имеет резервную Stop/Cancel для текущего UUID. Она проверяет отсутствие ID в AlarmKit. Это **не способ разбудить suspended приложение** и не доказательство слышимой длительности.
- Миграция ledger schema 1/2 → 3 отменяет прежние уведомления и AlarmKit alarms до новой постановки. Сохраняются настройки, голоса, дневник, исходное начало и интервал непрямого метода. Прошедшие события не повторяются.
- Новая schema-3 очередь сохраняется при обычном перезапуске. Ошибки чтения системной очереди не подменяются пустым списком.

## Почему прежний Stop мог не работать

В 0.9.1 короткий CAF уже был. Stop ожидался в процессе Luma через Task.sleep/опрос/alarmUpdates. При приостановке приложения iOS этот код не обязан исполняться к сроку. Конец файла сам по себе не подтверждает конец системного alarm state. Точный акустический механизм конкретного повтора без устройства и логов не установлен.

Замена CAF на WAV и отсутствие меток зацикливания — проверяемая гипотеза, а не обещание, что AlarmKit изменит собственное поведение. В этой работе документация Apple и интернет не открывались по просьбе пользователя.

## Запуск и обновление

Для системных сигналов нужен **iPhone с iOS 26+**. Сам интерфейс и данные сохраняют deployment target iOS 17; на старых iOS постановка сигналов недоступна. Собственное watchOS-приложение отсутствовало уже в основе; поведение системного будильника на паре iPhone/Watch проверяется отдельно.

1. Установить поверх старой Luma с тем же bundle ID com.sevchlenko.luma и прежней командой подписи. Не удалять приложение, если нужно сохранить данные.
2. Открыть приложение до ночи, разрешить будильники AlarmKit. После подтверждённой очистки старой очереди включить сохранённые сигналы в экране настройки.
3. В настройках поставить пробу через 60 секунд и заблокировать iPhone. Измерить реальную длительность внешним устройством; проверить отсутствие повторов минимум минуту.
4. Повторить с подключёнными Watch, затем проверить три события непрямого метода через 30 минут. При продолжающемся звонке использовать системную кнопку «Остановить» и сохранить диагностику.

До физической проверки не считать выпуск пригодным для ночного использования без наблюдения. Подробная матрица — Luma/Docs/DEVICE_TESTS.md. Отзыв тестировщика учтён в Luma/Docs/TESTER_FEEDBACK.md.

## Очередь и сохранность

Непрямой метод сохраняет интервалы 10–60 минут, по умолчанию 30 минут между началами событий. Планируется до 12 часов вперёд, в пределах общей очереди приложения из 60 событий. Это собственное ограничение Luma, не утверждение о лимите AlarmKit. Умные будильники и проба разделяют очередь. Пополнение происходит при выполнении приложения; бесконечная серия без открытия приложения не обещается.

Reservation сохраняется до await schedule; принятые ID проверяются. Намерение отмены записывается до обращения к системе. Остановка одного события не снимает будущие события серии. При неясном результате отмены новая постановка блокируется до повторной проверки.

Планировщик времени, REM-алгоритмы, темы, дневник, HealthKit, импорт и оригиналы записей сохранены из 0.9.4. REM всю ночь и собственный Watch runtime в этой ветке остаются выключены. Исправления Float32 обработки / PCM16 файла и LF/CRLF хешей из 0.9.4 сохранены.

## Сборка

Открыть Luma/Luma.xcodeproj в Xcode 26+ с iOS SDK 26+, выбрать схему Luma и свою прежнюю команду Automatic Signing. Bundle ID и entitlements сохранены.

На Mac выполнить из каталога Luma:

    python3 scripts/check-static.py
    python3 scripts/test-source-integrity.py
    python3 scripts/check-preserved-sources.py
    swift test
    bash scripts/check-audio-on-mac.sh
    bash scripts/check-finite-queue-on-mac.sh
    bash scripts/check-on-mac.sh

Последняя команда повторяет полный набор перед сборкой симулятора; для одного полного прогона достаточно её. Workflow дополнительно собирает generic iOS device без подписи и упаковывает IPA только после всех обязательных проверок.

Для GitHub Actions загрузить содержимое именно V.0.9.5 в корень репозитория, включая .github, .gitattributes и Luma, новым commit. Повтор запуска старого commit не применяет новые исходники. Workflow сохраняет macos-15-intel / Xcode 26.3 и проверяет, что IPA имеет 0.9.5 (21) и включает выделенный WAV. Новый CI run и IPA из этой среды не создавались.

## Проверки этой версии

В Windows выполнены Python тесты целостности, проверка исходников/ресурсов/проекта, разбор Swift/Bash/YAML и SHA-256 аудит исторических версий. Точные результаты — verification.json и Luma/Docs. Swift XCTest, AVFoundation harness, очередь с fake adapter, Xcode и физический iPhone здесь **не исполнялись**. Их наличие в проекте не равно успешному прогону.
